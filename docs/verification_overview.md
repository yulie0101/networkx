# Verification overview: `max_cardinality_matching_gabow`

A short summary of everything done to check that the implementation is
correct and runs within `O(sqrt(n) * m * alpha(n))`, for the project report
and presentation. Details are in `docs/change_review.md`,
`docs/cpp_provenance.md`, `docs/complexity_audit.md` and
`benchmarks/results/SUMMARY.md`.

## 1. Tests in `networkx/algorithms/tests/test_matching.py`

445 tests pass: 374 for our function and 71 original NetworkX tests.

| Group                             | Tests   | What it checks                                                                                                                                                                                                                                                   |
| --------------------------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Input handling and API            | 18      | Empty graph, single node, no edges, self-loops, isolated nodes, disconnected graphs, tuple and mixed node labels, directed graphs and multigraphs rejected, result is a set of edges, input graph not modified, same result on repeated calls and any node order |
| Graphs with a known answer        | 27      | Hand-checked small graphs, even cycles, special and named graphs (Petersen, hypercube, Desargues), complete and complete bipartite graphs, stars, regular graphs, single trees, greedy start at both extremes (already optimal, half of optimal)                 |
| Blossoms                          | 46      | Odd cycles alone, with a pendant, chained, nested up to depth 6, sharing a vertex or an edge, many disjoint ones, bridged triangles (Tutte-Berge), barbell, the graphs that historically broke `max_weight_matching`                                             |
| Random graphs against a reference | 85      | Random graphs from very sparse to dense, small and large, with self-loops and many components; result compared with `max_weight_matching` (and with exhaustive search on small graphs)                                                                           |
| Independent methods               | 31      | Bipartite graphs against Hopcroft-Karp; random trees and forests against an exact tree algorithm                                                                                                                                                                 |
| Scale and robustness              | 3       | Long paths and long odd cycles deeper than Python's recursion limit; memory grows less than quadratically                                                                                                                                                        |
| Instrumentation                   | 6       | The operation counters never change the result and are consistent                                                                                                                                                                                                |
| Regression and invariants         | 158     | The 10-node graph of the stale-bucket bug and 72 random variants; the 52 known failing graphs and 32 random ones with no stale bucket entry (pins the FIFO queue order); shortest augmenting path length strictly increases between iterations (Hopcroft-Karp)   |
| **Total (ours)**                  | **374** |                                                                                                                                                                                                                                                                  |
| Original NetworkX tests           | 71      | `max_weight_matching` (22), `is_matching` (26), `is_perfect_matching` (6), `is_maximal_matching` (4), `maximal_matching` (4), wrong graph types for the other functions (9)                                                                                      |

## 4. Plots (final numbers, per-graph medians)

| Plot | Question                                                                                       | Main result                                                                                                                                                                             |
| ---- | ---------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P1   | Does the number of iterations grow like `sqrt(n)`?                                             | Only on F5 from the C++ start: slope 0.52. Every other family is nearly flat (slope <= 0.12; 2-12 iterations)                                                                           |
| P2   | Is the work per iteration proportional to m?                                                   | Yes: work per iteration / m stays within a narrow band per family (F1 0.7-1.4, F2 1.7-3.1, F3-F6 2.6-6.3); F5's dips are the odd-clique effect                                          |
| P3   | Is the total work within `sqrt(n) * m`?                                                        | Yes: total work / `(sqrt(n) * m)` falls with n for every family; flat (about 3.2) only for F5 from the C++ start, where the bound is reached                                            |
| P4   | How does wall-clock time grow?                                                                 | Fitted slopes: Gabow 1.15-1.28 on F1, 1.92-2.17 (greedy off) on F2; Edmonds 2.06-2.26 on F1, 1.98-2.14 on F2                                                                            |
| P5   | Time divided by each bound: flat?                                                              | Gabow time / `(sqrt(n) * m)` and Edmonds time / `n^3` both fall with n (neither bound is tight on random graphs)                                                                        |
| P6   | How much faster is Gabow (greedy on) than Edmonds?                                             | F1 at 20,000 vertices: 142-378x. F2 at 800: 1.3-45x; 14 of 34 points are bimodal (bars). No point below 1                                                                               |
| P6b  | The same with an empty start (as in the paper)?                                                | F1 at 20,000: 37-134x. F2: Gabow is slower at all 25 points (0.30-0.96x), a constant factor of the Python code                                                                          |
| P8   | Wall-clock on the hard families?                                                               | Gabow (greedy on) beats Edmonds everywhere; F6 at 100,000: 0.7 s vs 1,582 s. From the C++ start on F5 (40,284 vertices): 94 s vs 205 s                                                  |
| P9   | Speedup on all families together?                                                              | Grows with n for F1 and every hard family: F3 25x, F4 10x, F5 560x, F6 2,234x at the largest size. F2 is bimodal (see P6)                                                               |
| P10  | Does the C++ start make F5 need `sqrt(n)` iterations, and does it explain the paper's Table 1? | 47, 69, 97, 139, 197 iterations for 5,026-80,180 vertices (slope 0.52); total work / `(sqrt(n) * m)` about 3.2; simulated C++ heuristic trigger gives exactly 24, 33, 47, as in Table 1 |

Not a plot: the stable check (F1, 10,000 vertices, Edmonds median of 3 runs,
Gabow median of 5) gives speedups of 8.6-72.9x (greedy off) and 26.5-119.6x
(greedy on).
